四、风险控制清单

① 风控是最需要盯的
BOSS 抓太频繁会弹验证码。缓解：每次请求后随机停顿 12~32 秒、单次运行条数封顶、 写操作每日上限 10 条、PAUSE 文件随时可停。被限流时第一件事是加大间隔，不是加并发。
② IP 不会因为独立 profile 而改变
独立 Chrome profile 只隔离登录态和 cookie，出口 IP 仍是同一个。 这一点必须提前说清楚，不能暗示能隐藏。
③ 投递是不可逆动作
三道门：allow_apply 开关（默认关）→ 一次性确认令牌（5 分钟、绑定 job_id） → 每日上限。没点头就不会发出去。
④ 简历不编造
prompt 里写死「只能用 profile.yaml 里真实经历中出现过的内容」，并要求每条 bullet 标注 「← 依据：」。生成物不会自动使用，你要自己看过才算数。
⑤ 简历文件不走大模型
上传的 .docx / .pdf 只在本地用规则解析（段落结构 + 字段关键词抽取）， 不发给任何模型，避免个人信息外泄。解析结果填成草稿，用户确认后才写入。
例外：「AI 根据经历推荐」按钮传的是从经历里提取的方向词， 不是原始简历文件，可以调大模型。这两条路径必须分开实现，别混了。
⑥ 投递参数下沉到每个平台
风控与安全配置按平台分开存（BOSS 是打招呼上限，智联是投递上限， 还有各自的专属项）。不存在一个全局开关覆盖所有站 —— 某站的限流规则和另一站根本不一样，用一个滑杆管全部站迟早出事。
⑦ 社区 adapter 会被覆盖
~/.bb-browser/sites/（私有）优先级高于 bb-sites/（社区）。 所有我自己写的、尤其带写操作的 adapter，都放私有目录，社区更新不会改掉行为。

六、开发阶段与验收

阶段交付物验收标准
T0跑通一次只读抓取 site boss/search 返回真实 JSON；失败就停下问你，不绕过登录
T1bb-browser 固定安装 + 包装脚本 bb.sh site list 列出平台
T2私有 adapter：boss/greet site info boss/greet 显示参数；抓包确认请求格式
T3插件骨架 hermes plugins doctor . --ci 退出码 0
T4matcher.py + 单测 完美匹配 ≥90 分；错城市错技能 <50 分；分数永不越界
公式：职位名 30 + 技能 30 + 城市 20 + 薪资 20（无经验项）
T5bbclient.py / storage.py 限速生效；同 job_id 重复插入不新增行
T6tools.py 工具集 全部返回 JSON 字符串、不抛异常
T7日报 + 简历 + 草稿 日报含分数与链接；简历每条带「← 依据：」
推送只发「岗位名 · 城市 + 链接」，不带分数与理由
T8投递两步协议 不带令牌不投递；令牌一次性、过期失效
T9多站 adapter zhaopin / huibo 各自返回统一词表 JSON
gxrc / cqrs 暂缓（用户 2026-10-26 决定）
T10挂 cron 到点推送，每条「岗位名 · 城市 + 链接」≤50 字（链接除外）； 连续两天不重复推同一岗位
T11设置页（HTML demo 已确认） 五个模块能读写配置；主题跟随 Hermes（宿主换皮肤插件跟着变）
T12简历文档本地解析 .docx/.pdf/.txt 解析出字段，不调用大模型；结果填成草稿待确认
T13AI 推荐岗位方向 / 技能 / 关键词 从「真实经历」提取；与简历导入区分，这里允许调大模型
T14简历模板库 + 渲染器 4 套模板；缩略图与实际输出同源；支持多选与 Agent 自动选模板
T15简历生成四步流程 读 JD → 挑要求 → 对照经历 → 按模板生成；不编造经历；投递仍需手动确认
T16投递两路径 + 历史简历推荐 已优化 → 直接投优化版；未优化 → 弹历史简历并按对该岗匹配分排序； 无历史简历 → 引导去优化
T17用户简历档案（PDF + 标签） 投递成功的简历自动存 PDF 并打标签；列表能预览 / 下载 / 设默认； 标签可被 resume_matcher 读取
T18自定义模板转换 .docx 抽版式 → HTML 模板；.pdf / 图片 → 底图+文本层； 转换后进模板库，与内置模板同一套渲染器
给你的确认点
1. 设置页 UI（job-radar/设置页-demo.html）看得过吗？哪里要调
2. 后端先做哪块 —— 我建议 T11 设置页 + T16 投递两路径，因为这两块最贴近你的日常使用
3. 风险档位默认「只读」，要不要一开始就开「半自动」？
4. profile.yaml 里你的真实经历，谁来写？你口述我来填也行。

  • 每份记录：文件名 / 日期 / 用的模板 / 投递几家 / 几家回复 / 标签
  • 操作：预览、下载、设为默认

  • 允许投递简历（默认关）
  • 每日投递上限（BOSS 是「打招呼上限」，智联是「投递上限」）
  • 跳过外包 / 劳务派遣
  • BOSS 专属：遇到风控自动降速（code 37 → 间隔拉到 60 秒 + 通知）
  • 智联专属：抓取详情页开关（关掉快 3 倍但没 JD）

③ 广西人才网、重庆人社 暂不接入，不出现在平台列表里。

② 没有独立的「定时推送」模块。定时与推送的所有细项 （自动抓取开关、只推当天新岗位、每次最多几条、失败也通知、抓取时段） 全部整合进「推送内容」面板右上角的「高级」按钮，默认折叠。 面板标题栏只留一句摘要（例：每 6 小时 · 下次 13:02）。
③ 推送格式精简：每条消息只含 岗位名 · 城市 + 岗位链接， 不带分数、不带命中理由。一条岗位一条消息，不合并。
④ 链接不计入 50 字限制。
⑤ 日报 Markdown 文件里保留完整明细（分数、命中、缺口、链接），推送只是索引。
主题（用户 2026-10-26 明确）
设置页不提供自己的主题选择器，只跟随 Hermes：在 Hermes 设置里换皮肤， 插件 UI 同步变化。实现方式 = CSS 直接消费 Hermes 桌面的 --dt-* 变量， 宿主切皮肤时变量一变，插件页自动跟着变。

八、简历生成流程

由岗位卡上的「简历匹配优化」触发，四步，每步都能中止。

步动作约束
1读该岗位 JD 全文从已登录的浏览器取，不额外登录、不重新抓列表
2挑出 JD 核心要求技能 / 学历 / 年限 / 关键词
3对照用户经历，标出可写进简历的点 只重组用户写过的内容，不编造没出现过的经历
4按模板生成简历 模板来自「用户简历」模块；开启智能选模板时由 Agent 按 JD 挑版式
投递永远是另一道手动确认。生成 ≠ 投递。生成结果先给预览， 用户确认后才保存/导出；投递仍需单独点头。关闭「允许投递简历」时插件永远只读。

九、投递与简历档案流转（2026-10-26 新增）

「简历匹配优化」与「投递简历」拆成两个独立动作，投递会留下档案。

场景用户看到什么系统做什么
先优化，再投递
推荐路径		 点「简历匹配优化」→ 走四步流程 → 完成后点「投递简历」 该岗位标记为 optimized，投递时直接用优化后那份，不再询问。 投递成功后存 PDF + 打标签进「用户简历」
直接投递，没优化过 点「投递简历」→ 弹历史简历推荐：列出历史简历， 每份显示对该岗位的匹配分，默认选中最高分那份 用 resume_matcher.py 给每份历史简历按标签 × 岗位要求打分排序。 用户选定后投递该份，并同样存 PDF + 打标签
只有两态，不做第三种。用户自己会判断 —— 历史简历列表为空时， 弹层自然显示空列表，用户看到「没有可用简历」就明白了，不需要专门做一个 「引导去优化」的分支。少一个分支少一份逻辑。
简历标签从哪来：投递时把「目标岗位方向 + 该岗 JD 命中技能 + 岗位关键词」 打成标签存在 PDF 简历旁边。下次遇到类似岗位时，resume_matcher.py 用这些标签去打分 —— 这就是「历史简历推荐」的排序依据。 标签只从真实经历和实际命中项来，不凭空生成。
投递依然是不可逆动作。不管走哪条路径，都必须过三道门： 每站自己的「允许投递简历」开关（默认关）→ 一次性确认令牌 → 该站每日上限。 选了历史简历不等于授权投递 —— 选定后还要走确认。

十、版本管理与发布（2026-10-26 起）

项目要开源到 GitHub，仓库结构、脱敏规则、发布流程固定下来。

项规则
仓库名 Good-job-Ez，中文名「好岗好找」
仓库结构 src/job_radar/ 插件本体（含 tests/）
docs/ 开发文档、流程图 PDF、设置页 demo、抓取层现状
examples/ 示例与配置模板
脱敏规则 仓库里不得出现：真实姓名、手机号、邮箱、本机绝对路径、 真实公司名、cookie 值、真实经历原文。
演示数据一律用「张三」「某人力资源有限公司」「user@example.com」这类占位。
profile.yaml（个人画像）只提交 profile.example.yaml， 真身进 .gitignore。
.gitignore 排除 profile.yaml / resume/ / uploads/ / jobs.db / reports/ / *.docx / *.pdf（docs 下的例外）/ __pycache__ / .env / node_modules/ / sites/（私有 adapter）
.gitattributes 统一 eol=lf，避免跨平台 diff 噪音；二进制文件标 binary
许可 MIT
提交规范 Conventional Commits：feat: fix: docs: refactor: chore:
发布前必查：
① git ls-files 里没有 profile.yaml、jobs.db、任何 .docx
② 全仓扫一遍真实姓名 / 手机号 / 邮箱 / 本机路径 / 真实公司名
③ python -m unittest discover -s tests 全过
④ README 里的安装步骤在干净环境能走通
